# ADR-006: Estrategia de Sincronización Offline (Eventual Consistency)

**Estado:** Aceptado
**Fecha:** 2026-08-02
**Autores:** Equipo MODO YO
**User Stories relacionadas:** US-012, US-003, US-009

## Contexto y Problema
Los adolescentes usan la app en movimiento con conectividad intermitente. El progreso (ejercicios completados, XP, rachas) debe registrarse aunque no haya conexión y no perderse nunca (US-012). Se necesita una estrategia de sincronización clara para evitar pérdida de datos y conflictos.

## Alternativas Consideradas
1. **Online-only (requiere conexión)** — Contras: inaceptable; rompe US-012 y frustra al usuario.
2. **Sincronización bidireccional en tiempo real** — Pros: datos siempre frescos. Contras: complejidad alta, innecesaria para el tipo de datos (mayormente append-only).
3. **Write-local-first + sync asíncrona (eventual consistency) (elegida)** — Pros: UX fluida offline, simplicidad razonable. Contras: requiere resolución de conflictos.

## Decisión
Adoptar **write-local-first con consistencia eventual**: las escrituras se guardan primero en el almacenamiento local (Zustand persist) y se sincronizan con Supabase de forma asíncrona al detectar conexión.

## Consecuencias
- **Positivas:** La app funciona sin conexión; sin pérdida de progreso; buena percepción de rendimiento.
- **Negativas/Riesgos:** Posibles conflictos de datos; estados temporalmente divergentes entre dispositivo y servidor.
- **Mitigaciones:** Datos de progreso mayormente **append-only** (`daily_logs`); usar `timestamp` e idempotencia por `exercise_id`+fecha; estrategia last-write-wins para campos escalares (`xp`, `streak_count`) recalculados desde los logs cuando sea posible.

## Notas Técnicas
- Cola de operaciones pendientes en el store; reintento al reconectar.
- Idempotencia en `POST /progress/complete` para evitar doble conteo de XP.
